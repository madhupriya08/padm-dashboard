PADM Sign-Off Dashboard

A Streamlit-in-Snowflake app that replaces the manual Excel sign-off process for monthly direct-mail credit-card campaigns — 7 tabs, one campaign at a time, every write versioned and audited.

Overview

The real, running code is the padm/ package (padm/tabs/*.py, padm/repository.py, padm/ui.py, padm/formulas.py). A separate app/ tree exists in the project but is dead code — not imported by streamlit_app.py — kept only for historical reference. Every change on this page is to padm/.

Two-schema design

Working Schema (DB_RISK.RISK_SBX) is where every tab reads and writes. An Archive Schema concept exists for finalized, read-only history per the sign-off proposal.

Versioned, never overwritten

Assumptions, selections, allocations and segments are all append-only version tables — a save never deletes the prior row, it retires it.

One audit trail

DM_PADM_CHANGE_EVENT is written to by every write-path across every tab — a single place to answer "who changed what, and why."

Where the data actually comes from

Two source systems feed PADM's own tables, which the dashboard reads — the dashboard itself never queries the source systems directly except through governed views.

Demo Q&A prep

The questions you asked, plus the ones most likely to come up alongside them.

QDid we fetch any data from Vivian's code, and from where exactly?
Not as a live data source — her NRR/Unwinds SQL scripts are legacy ETL reference, not tables the app queries. What's confirmed: VW_PADM_SEGMENT_SOURCE_CANDIDATE's segment-naming logic (the MLA / PCO / PCL / PDCL / ABDN / REMAIL suffixes) matches her classification scheme conceptually — but the actual score-band/prospect-type classification happens upstream, in whatever already populates T_EXPERIAN_MAILFILE / T_TRANSUNION_MAILFILE's PROSPECT_TYPE/PRESCREEN_VANTAGE_* columns, not inline in her script. Her Unwinds_optimized scripts are background for the Unwind Rate assumption only.
QWhere did all the campaign and segment information come from?
Campaigns: discover_campaign() merges VW_PADM_ACM_CAMPAIGN_CANDIDATE (ACM offer data, eligibility-filtered) into DM_PADM_CAMPAIGN_1 — this already existed. Segments: historically only ever created by hand through the Create Segment form. This session added the equivalent sync for segments — discover_segments(), sourced from VW_PADM_SEGMENT_SOURCE_CANDIDATE, which reads the real Experian/TransUnion mailfile tables directly.
QAre segment-level assumptions stored anywhere for completed campaigns?
Yes — DM_PADM_SEGMENT_ASSUMPTION_VERSION is fully versioned and append-only; nothing is ever deleted. A completed campaign's segment assumptions stay queryable forever via "Version history." Once a campaign reaches APPROVED, the whole app goes read-only (campaign["locked"]), but the underlying data isn't purged — only editing is blocked.
QWhat happens once a campaign is approved — can it still be changed?
No, by design. The confirmed real status flow only allows REJECTED → DRAFT — there's no procedure path from APPROVED back to editable. Every input across every tab already disables itself automatically (disabled=locked), and the header shows a lock banner. A "reopen an approved campaign as a new version" workflow doesn't exist today — it would be new scope, not a toggle.
QCan the same offer really belong to two different segments?
Yes, as of this session, by explicit decision. Its full Quantity/Boards/Marketing Expense etc. count independently in each segment — so a campaign's Grand Total can be larger than the true count of distinct offers mailed. That's expected, not a double-counting bug.
QIs LIFT a real option for both Experian and TransUnion?
It shows in the dropdown for both, per an explicit UI decision. Technically, Credit One's own data dictionary confirms LIFT_SCORE exists only in T_EXPERIAN_MAILFILE — TransUnion has no real score-band data behind it yet, so creating a TransUnion + LIFT segment will correctly show "no active score-range rules" until real data is added.
QWhy do some Signature Page / Segment Viewer cells show blank instead of 0?
Intentional, matching the real Segment.xlsx convention — only non-zero values are shown on calculated grids. The Selection % input grid is unchanged (it never did this).
QWhat's the difference between Working Version and Final Version on Segment Viewer?
Real, confirmed difference, not a redundant toggle — the sign-off proposal's own Working-vs-Final table says so. Working Version = Selection % × Universe Post-EMS (your estimate). Final Version swaps in actual mailed quantities from DM_PADM_MAILFILE_CELL (sourced from the real Experian/TransUnion mail files) once they exist.
